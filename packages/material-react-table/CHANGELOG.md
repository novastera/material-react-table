# Changelog

## 5.0.0

This release moves the table engine from `@tanstack/react-table` v8 to **v9** (and `@tanstack/match-sorter-utils` from v8 to v9 alongside it), migrates column/row drag-and-drop onto `@dnd-kit`, adopts React Compiler for automatic memoization, and rebuilds how row/cell/header/footer rendering subscribes to table state so that interacting with one part of a large table (selecting a row, resizing a column) no longer re-renders the whole thing. This is a hard break with no backward-compatibility shim — see `MIGRATION.md` for a step-by-step upgrade walkthrough with before/after code for every item below; this file is the terse reference.

### Breaking changes

- **TanStack Table v9** (the underlying engine):
  - **Column pinning state**: `columnPinning: { left, right }` is now `columnPinning: { start, end }`, everywhere — `initialState`/`state`, `onColumnPinningChange`, `column.pin('left' | 'right' | false)` → `column.pin('start' | 'end' | false)`, `column.getIsPinned()` returns `'start' | 'end' | false`. Row pinning (`top`/`bottom`) is unaffected — it's a different feature.
  - **Sorting**: column-def `sortingFn` is now `sortFn`. The table-level `sortingFns` option is now `sortFns`. `MRT_SortingFn`/`MRT_SortingFns` are now `MRT_SortFn`/`MRT_SortFns`.
  - **Column sizing/resizing**: the `columnSizingInfo` state slice is now `columnResizing` (react-table itself split sizing and resizing into separate features/state in v9). `MRT_ColumnSizingInfoState` is now `MRT_ColumnResizingState`. `table.setColumnSizingInfo` is now `table.setColumnResizing`.
  - **Table instance methods renamed** to match v9:
    - `getLeftLeafColumns`/`getRightLeafColumns` → `getStartLeafColumns`/`getEndLeafColumns`
    - `getPaginationRowModel`/`getPrePaginationRowModel` → `getPaginatedRowModel`/`getPrePaginatedRowModel`
  - **Multiple aggregation functions per column** (`aggregationFn: ['min', 'max']`) are now handled natively by react-table v9 and produce a **keyed object result** (`{ min, max }`) instead of v8's positional array (`[min, max]`). Update any custom `AggregatedCell`/`Cell` renderer that indexed the result by position (`value[0]`, `value[1]`) to use the named keys instead.
  - **`table.getState()`**: react-table v9 removed this method in favor of a reactive `table.state` property. Most of this library's own state (density, editing state, action cell, hover/drag tracking, etc.) is now registered as a real TanStack v9 feature, so `table.getState()` is a genuine native method backed by the same atom/store system as everything else — no change needed for consumers, including headless/manual-rendering usage via `header.getContext()`/`cell.getContext()`/`row.getContext()`. Two narrow exceptions remain plain React state rather than atoms (both are read synchronously before the table is constructed each render, which atoms can't support without a one-render lag): `columnFilterFns` and `globalFilterFn`. If a custom `Header`/`Cell` built through `getContext()` reads either of those, or the pure consumer-passthrough loading flags (`isLoading`, `showSkeletons`, `isSaving`, `showLoadingOverlay`, `showProgressBars`, which have never had internal state of their own), override `table` explicitly in the context object to be safe:
    ```tsx
    flexRender(columnDef.Header, { ...header.getContext(), table })
    ```
    This does not affect the standard `<MaterialReactTable>` component, or any headless usage that already passes `table` down as an explicit prop instead of reading it off `getContext()`.
  - **`enableFacetedValues`**: because react-table v9 features must be registered once, statically, this library can no longer conditionally skip registering the faceted-values row models. The `enableFacetedValues` option still works exactly as before (faceted unique values / min-max are only computed when it's `true`) — the gating just moved from registration time to read time. No consumer-facing change, noted here only because of the internal architecture shift.
- **Render/subscription architecture: `useTable()` replaced internally by context + `Subscribe` boundaries.** Selecting a row, pinning a row, entering edit mode, etc. previously re-rendered every cell in the table, because the table's own returned object got a new identity on every state change anywhere, and several row/cell components subscribed to whole shared state objects rather than a value scoped to that specific row/column. Both are now fixed: internal construction moved to TanStack's `createTableHook`/`useAppTable` (from `useTable`), and row/cell/header/footer rendering goes through dedicated boundary components (`table.AppCell`/`table.AppHeader`/`table.AppFooter`, plus this library's own `AppRow` equivalent) whose subscriptions are narrowed to one specific row/column/cell. Consumer-facing consequences:
  - **`table.state` now always returns `{}`.** `table.getState()` is **unaffected** — it reads the live store directly and continues to work exactly as documented above. If you read `table.state.X` anywhere (in a custom `Header`/`Cell`, a `muiTableProps`-style callback, or headless usage), switch to `table.getState().X`.
  - **`MRT_TableBodyRowProps`, `MRT_TableBodyCellProps`, `MRT_TableHeadCellProps`, and `MRT_TableFooterCellProps` no longer accept `row`/`cell`/`header`/`table` as props** — each component reads them from context instead, provided by whichever internal component wraps it (`MRT_TableBody`, `MRT_TableBodyRow`, `MRT_TableHeadRow`, `MRT_TableFooterRow`, respectively). This does not affect the standard `<MaterialReactTable>` component, `columnDef.Cell`/`Header`/`Footer`/`AggregatedCell`/etc. render props, `header.getContext()`/`cell.getContext()`/`row.getContext()`-based headless rendering, or `MRT_TableBodyCellValue` (unaffected — still takes `cell`/`table` as plain props, see `MIGRATION.md` for the still-supported manual-`<TableBody>` pattern). It only affects code that directly imports and renders `<MRT_TableBodyCell>`/`<MRT_TableHeadCell>`/`<MRT_TableFooterCell>` themselves; see `MIGRATION.md` for the replacement pattern using `table.AppCell`/`table.AppHeader`/`table.AppFooter`. `<MRT_TableBodyRow>` currently has no standalone public boundary to satisfy its row context on its own — render the whole `<MRT_TableBody>` instead if you need row-level composition.
  - `useMaterialReactTable()` — the hook almost every consumer actually calls — has the **same signature** as before and still returns an `MRT_TableInstance`; this change is internal to it. The returned instance additionally carries `table.AppCell`/`table.AppHeader`/`table.AppFooter`/`table.AppTable` — new, additive capability.
- **`memoMode` removed.** React Compiler now handles component-level re-render avoidance automatically (see "Also updated" below), making this hand-rolled `'cells' | 'rows' | 'table-body'` memoization option redundant. If you were setting it explicitly, remove it — there's no replacement option, since it's no longer needed.
- **React/React DOM peer dependency floor raised to `>=19.3`** (previously `>=19.0`). Required for `useEffectEvent` (stable since 19.2, with a bug fix for `forwardRef`/`memo` components landing in 19.3) and to pick up that fix for the hook this library now uses internally (see "Also updated" below).
- **Column/row drag-and-drop now uses [`@dnd-kit`](https://dndkit.com/)** internally instead of the native HTML5 Drag and Drop API, matching TanStack Table's own official Column/Row DnD examples. This changes two exported types:
  - **`MRT_GrabHandleButtonProps`**: `onDragStart`/`onDragEnd: DragEventHandler<HTMLButtonElement>` are replaced with `listeners?: DraggableSyntheticListeners`, `attributes?: DraggableAttributes`, and `activatorRef?: Ref<HTMLButtonElement>` (dnd-kit's own types, re-exported from `@dnd-kit/core`). If you render `<MRT_GrabHandleButton>` directly or wrap it, update accordingly.
  - **`muiColumnDragHandleProps`/`muiRowDragHandleProps`**: their `onDragStart`/`onDragEnd` callbacks now receive dnd-kit's `DragStartEvent`/`DragEndEvent` instead of a native `DragEvent`. If you only used `onDragEnd` to read `table.getState().draggingRow`/`hoveredRow` (the documented row-reorder-commit pattern), no change is needed — only code that inspected the native event object itself is affected.
  - `draggingColumn`/`draggingRow`/`hoveredColumn`/`hoveredRow` state, their `on*Change` callbacks, `enableColumnDragging`/`enableRowDragging`/`enableColumnOrdering`/`enableRowOrdering`, and the row-reorder commit pattern via `muiRowDragHandleProps.onDragEnd` are all **unchanged**.
  - New: column and row reordering are now keyboard-accessible (focus a grab handle, `Space` to pick up, arrow keys to move, `Space` to drop) — native HTML5 DnD had no keyboard equivalent.
  - Minor scope change: a column reorder must now be dropped on a header cell specifically (previously, dropping anywhere in the column's body also worked). The visual highlight down the whole column during a drag is unchanged.

### Also updated

- **React Compiler is now part of this library's own build.** `material-react-table`'s bundle is compiled with `babel-plugin-react-compiler` (targeting React 19, which this library already requires), so components get automatic memoization equivalent to hand-written `useMemo`/`useCallback`/`React.memo` without needing to write it. This is an internal build/performance change — no consumer-facing API changed. As part of enabling this, most components had pre-existing Rules-of-React issues fixed (reading refs during render for sticky header/footer positioning, manually-memoized values with incomplete dependency arrays, a `debounce()` misusing `useCallback`) so the compiler can actually optimize them instead of skipping them.
- **Bugfix**: a consumer-supplied `inputRef` in `muiSearchTextFieldProps` (the global filter text field) is now actually forwarded to the underlying input. It was previously always silently dropped due to an ineffective ref-merge.
- **Bugfix**: column resizing now actually updates every cell's rendered width. Two compounding causes, both fixed: the CSS custom properties every cell's width reads from weren't recomputing on resize (now written imperatively via a `columnSizing` atom subscription, matching TanStack's own "column-resizing-performant" pattern), and separately, the `flex`/`width`/`min-width` styles derived from those variables were being silently dropped due to an array/object mismatch in how they were merged into each cell's `sx` prop.
- **Bugfix**: clicking a row's Edit button (`editDisplayMode: 'modal'`) no longer throws `row.getAllCells is not a function`. Caused by `setEditingRow({ ...row })` — spreading a TanStack `Row` drops its prototype-based methods, leaving a plain data object.
- **Bugfix**: a row using `renderDetailPanel` with no hierarchical `subRows` can now actually be expanded — clicking its "Expand" button previously did nothing. The button's own disabled-state logic already accounted for `renderDetailPanel`, but the underlying `row.toggleExpanded()` is gated by TanStack Table's `getCanExpand()`, which only recognizes `subRows.length` unless `getRowCanExpand` is provided. This library now supplies a default `getRowCanExpand` that also accounts for `renderDetailPanel`; an explicit `getRowCanExpand` you provide still takes precedence.
- **Bugfix**: pinning or hiding a column now reliably updates the table header, footer, and every row — not just the cells that happened to re-render for an unrelated reason. Several internal components called TanStack methods that read column pinning/visibility/order state without subscribing to it, which the render-stabilization work above surfaced as real, visible staleness (a moved-but-not-visually-moved header column; a hidden column leaving a stale, mismatched extra cell in every row) rather than being masked by the broad re-rendering that no longer happens.
- **Bugfix**: pinning a row, and entering/exiting create or edit mode on a row's action cell, now update exactly that row rather than needing a coincidental re-render elsewhere to pick up the change — a side effect of a redundant subscription duplicating (and silently undoing) the new row/cell-scoped boundary's own narrowed subscription for the same state, found auditing the render architecture above.
- **Bugfix**: column/row drag-and-drop now actually shows the dragged item (and its shifting siblings) moving during the drag, instead of visually doing nothing until drop. `useSortable()`'s computed `transform`/`transition` were never applied to the DOM in three places (`MRT_TableBodyRow.tsx`, `MRT_TableHeadCell.tsx`, `MRT_ShowHideColumnsMenuItems.tsx`) — the reorder always committed correctly on drop, but nothing visually tracked the drag beforehand.
- **New**: `reorderRows(data, draggingRow, hoveredRow)` exported utility for committing a row drag-and-drop reorder. Row reordering still has no first-class state (`data` remains fully consumer-owned, exactly as before) — this just replaces the ~8-line splice every row-reordering example previously hand-wrote inside `muiRowDragHandleProps.onDragEnd` with one call: `setData((prev) => reorderRows(prev, draggingRow, hoveredRow))`.
- `useMRT_ObservedElementSize` (used internally for sticky header/footer/toolbar height measurement) now uses React's `useEffectEvent` instead of a hand-rolled ref-mirroring pattern — behaviorally identical, just using the now-stable primitive this pattern already existed to approximate.
- `@tanstack/react-virtual`'s `useVirtualizer()` is isolated behind a `'use no memo'`-marked wrapper (React Compiler's documented escape hatch for third-party imperative-handle APIs it can't safely auto-memoize), so the rest of the row/column virtualization hooks are fully compiler-optimized instead of being skipped wholesale.
- `@faker-js/faker` (dev-only) bumped to v10. No consumer-facing impact — this only affects the Storybook demo data.
