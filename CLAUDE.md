## TanStack Table v9: the core model

State lives in `@tanstack/react-store` atoms, not component state. The table instance is built once and never rebuilt. Row/cell/header/footer rendering is scoped through context-plus-`Subscribe` boundaries, not props threaded down from the root.

- **`useAppTable(options, selector?)`** (`src/hooks/useMRT_AppTable.ts`, a module-scope `createTableHook({features: MRT_TableFeatures})` call) constructs the table. The persistent "core" table object (`constructTable(...)`) is created once via `useState`'s lazy initializer and never recreated — every method on it and every entry in `table.atoms` is a **stable reference for the table's lifetime**.
- The object `useAppTable()` returns each render is a fresh wrapper carrying `state` (from `useSelector(rootSource, selector, {compare: shallow})`) plus `.AppTable`/`.AppCell`/`.AppHeader`/`.AppFooter`. **Omitting `selector` subscribes to every registered state slice**, giving the wrapper a new identity on every atom write anywhere in the table. `useMRT_TableInstance.ts` passes a constant selector (`() => ({})`) to keep the wrapper referentially stable regardless of what atoms are written.
- **Row/cell/header/footer rendering goes through a boundary component with a narrowed `selector`.** `table.Subscribe` (`useSelector(source, selector, {compare: shallow})`, then `children(selected)`) re-renders in isolation when the selector's *output* changes, without forcing its parent to re-render. `AppCellImpl`/`AppHeaderImpl` wrap this: a `Context.Provider` (descendants read `cell`/`header` via `useCellContext()`/`useHeaderContext()` instead of as a prop) plus, when given a `selector`, a `Subscribe` around `children`. TanStack ships table/cell/header/footer boundaries this way; `MRT_AppRow` (`src/hooks/useMRT_AppRow.tsx`) is the matching row boundary, built the same way for the one boundary `createTableHook` doesn't cover. The four call sites that instantiate rows/cells/headers/footers — `MRT_TableBody.tsx` (rows), `MRT_TableBodyRow.tsx` (cells), `MRT_TableHeadRow.tsx` (headers), `MRT_TableFooterRow.tsx` (footers) — each wrap in the matching boundary with a `selector` narrowed to exactly what it needs, keyed by `row.id`/`column.id`/`cell.id`.
- **Inside a boundary, an atom the boundary's own selector already narrows should be read live (`table.getState()`), not re-subscribed to.** A descendant's own bare `useSelector(table.atoms.X)` for an atom the ancestor boundary already covers doesn't just waste a render — it re-fires on *any* row's/column's change to that atom, undoing the boundary's narrowing for that one descendant. Check what the boundary's own `selector` prop (at its call site, one of the four files above) already covers before adding or removing a subscription inside it.
- **Not everything is inside a boundary.** Components rendered once, table-wide (containers, toolbar, the head/footer wrappers themselves) still use a bare `useSelector(table.atoms.X)` — correct for state that isn't row/column-scoped (`density`, `isFullScreen`, `isLoading`/`showSkeletons`, `columnVisibility`/`columnOrder`/`grouping`, which reshape the whole rendered set rather than one row).
- **`table.atoms.<key>`** — each piece of state (`sorting`, `columnSizing`, `rowSelection`, `columnResizing`, `grouping`, `pagination`, `expanded`, `rowPinning`, `columnPinning`, plus this library's own `isLoading`/`showSkeletons`, ...) is its own atom. Reference: [TanStack Store atoms](https://tanstack.com/store/latest/docs/framework/react/examples/atoms), [`useSelector`](https://tanstack.com/store/latest/docs/framework/react/reference/functions/useSelector.md).
- **`useSelector(atomOrStore, selector?, options?)`** is the read hook — subscribes a component to just that atom (or a narrowed slice of it). `options.compare` defaults to reference equality; boundary selectors and the table's own wrapper use `{compare: shallow}`.
- Any TanStack *method* call made during render to decide what to display (`column.getIsPinned()`, `row.getIsSelected()`, `column.getIsSorted()`, ...) reads a live atom internally but **does not itself subscribe your component to it**. Something in the component's boundary chain — the boundary's own `selector`, or a bare `useSelector` if outside any boundary — has to subscribe, or the component won't re-render when it changes.
- **Calls inside event handlers/effects are fine as plain `table.getState()`/`table.atoms.X.get()`** — they only need the current value at execution time, not reactivity. Don't add `useSelector` there.
- **`table.getState()`** always returns the live snapshot (a method on the stable core object) but never triggers a re-render by itself. Don't use it during render to decide what to display unless an ancestor boundary's selector already guarantees the re-render.
- **`table.state`** (the property) is intentionally always `{}` — a consequence of the constant selector above. Read `table.getState()` instead, everywhere.
- Column-def-construction functions (`prepareColumns`, `getMRT_Row*ColumnDef`, `showRow*Column`) are **not** components — they run inside a `useMemo` in `useMRT_TableInstance.ts` and should stay that way; don't reach for atoms/selectors inside them.
- **`columnDef.Cell`/`Header`/`Footer`/`AggregatedCell`/etc. render props are plain functions** (`columnDef.Cell?.({cell, column, row, table})`) — they don't participate in the boundary mechanics above.
- Table features (sorting, grouping, row selection, this library's own custom state) are registered via `tableFeatures({...})` and passed as the `features` option — not bundled by default like v8. See `src/utils/tableFeatures.ts` and `src/utils/mrtStateFeature.ts`.
- **Do not run `babel-plugin-react-compiler` in this library's Rollup `dist` build.** `row`/`cell`/`table` are stable identities; UI reads like `row.getIsSelected()` / `table.getState()` are interior mutability. The compiler caches those calls against the object, so a discarded `useSelector(table.atoms.rowSelection)` (subscribe-only, return value unused) never invalidates `checked` / `data-selected`. Storybook (source) was fine; every consumer of compiled `dist` was not. Re-render scoping is `table.Subscribe` / `AppCell` / `AppRow`. Keep source Rules-of-React clean (eslint `react-hooks`) so a *consumer app* that runs the compiler on its own code is safe; `'use no memo'` wrappers around `useVirtualizer()` stay for that case. Never bake the compiler into `dist`.
- **`@tanstack/react-virtual`'s `useVirtualizer()`** returns functions that close over internal mutable state and can't be safely auto-memoized by React Compiler — isolate any direct call to it behind a `'use no memo'`-marked wrapper (see `useMRT_UnmemoizedRowVirtualizer.ts`/`useMRT_UnmemoizedColumnVirtualizer.ts`).
- Public rendering components (`MRT_TableBodyCellProps`, `MRT_TableHeadCellProps`, `MRT_TableFooterCellProps`, `MRT_TableBodyRowProps`) don't accept `row`/`cell`/`header`/`table` as props — they read them from the boundary context above. `table.AppCell`/`table.AppHeader`/`table.AppFooter` are the public way to render one of these standalone; see `MIGRATION.md` for the pattern.
- Docs: [TanStack Table v9 migration guide](https://tanstack.com/table/latest/docs/guide/migrating), [`useTable`/`useAppTable` reference](https://tanstack.com/table/latest/docs/framework/react/reference/functions/useTable), [`createTableHook`](https://tanstack.com/table/latest/docs/framework/react/guide/composable-tables), [TanStack Store reference](https://tanstack.com/store/latest/docs/reference/index).

## MUI v9: styling is `sx`-first

MUI v9's own docs are explicit: **prefer `sx` and the `styled` utility over other styling approaches**; don't assume a pattern from an older MUI major without checking. [Customization overview](https://mui.com/material-ui/customization/how-to-customize/), [`sx` usage](https://mui.com/system/getting-started/the-sx-prop/).

- **`sx` accepts an array**, and MUI's own docs prefer array syntax over object-spreading multiple style sources together — falsy entries are ignored, styles merge correctly. Spread an array-returning helper as array entries: `sx={[...getCommonMRTCellStyles(...), otherStyles]}`, never `sx={[{...getCommonMRTCellStyles(...)}]}` (that silently produces numeric keys the `sx` engine doesn't understand). See `src/utils/style.utils.ts`'s `getCommonMRTCellStyles` and any `MRT_*Cell.tsx` for the pattern.
- **For highly dynamic values that change on every frame (drag/resize), use inline CSS custom properties, not `sx` objects with changing values** — MUI's own guidance. Column/header widths are written as `--col-<id>-size`/`--header-<id>-size` CSS variables via a `useLayoutEffect` + `table.atoms.columnSizing.subscribe(...)` in `MRT_Table.tsx`, imperatively through `element.style.setProperty(...)`, matching [TanStack Table's own "column-resizing-performant" example](https://tanstack.com/table/latest/docs/framework/react/examples/column-resizing-performant).
- MUI's plain `<Table>`/`<TableCell>` map to native `<table>` elements and are what this library builds on, not `DataGrid` — see [MUI Table docs](https://mui.com/material-ui/react-table/). For huge datasets, MUI points at virtualization (this library uses `@tanstack/react-virtual`, not `react-virtuoso`).
- `unstable_memoTheme`-style patterns (MUI memoizes theme-only style functions internally) mean passing stable `theme`-callback functions to `sx` is cheap — don't hand-roll extra memoization around `sx` callbacks.

## `@dnd-kit`: column/row drag-and-drop

Native HTML5 `draggable`/`dragstart`/`dragenter` isn't used (no keyboard support, and react-virtual can unmount the dragged node mid-drag) — `@dnd-kit/core` + `@dnd-kit/sortable` instead, matching [TanStack Table's own Column/Row DnD examples](https://tanstack.com/table/latest/docs/framework/react/examples/column-dnd).

- One shared `<DndContext>` (`useMRT_DragAndDrop.ts`) wraps the whole table; `active.data.current` carries `{type: 'column'|'row', column|row}` so one context discriminates both drag kinds.
- Header cells / body rows register via `useSortable({id, data: {...}})`; the toolbar's group-by drop zone is a plain `useDroppable`.
- dnd-kit tracks the active drag via document-level pointer/keyboard listeners, not a listener on the dragged DOM node.
- `onDragOver` only fires when the resolved drop target actually *changes*, not on every pixel of pointer movement (unlike native `dragenter`).
- **`useSortable()` only *computes* a drag-shift `transform`/`transition` — it never applies them to the DOM.** The destructured `attributes`/`listeners`/`setNodeRef` alone make the item draggable and let dnd-kit track the drag internally, but the item won't visually move unless you also destructure `transform`/`transition` and apply `style={{transform: CSS.Transform.toString(transform), transition}}` (from `@dnd-kit/utilities`) to the sortable element. If a row is also virtualized, combine dnd-kit's transform with the virtualizer's own `translateY` rather than letting one overwrite the other (see `MRT_TableBodyRow.tsx`'s `rowTransform`) — build this with plain `if` statements into a variable above the JSX, not a ternary-per-element `.filter(Boolean).join()` (React Compiler rejects that shape).
- **`enableRowDragging` alone does not enable committing a reorder** — only `enableRowOrdering` populates `hoveredRow` (see `useMRT_DragAndDrop.ts`'s `handleDragOver`), which `muiRowDragHandleProps.onDragEnd` needs to read to know where to drop. `enableRowDragging` shows the grab handle and lets dnd-kit track/animate the drag, with no built-in drop target — a narrower "just show the handle, I'll wire my own logic" flag vs. `enableRowOrdering`'s full built-in support. Same distinction for columns (`enableColumnDragging` vs `enableColumnOrdering`).
- Reference: [dnd-kit docs](https://dndkit.com/), [`useSortable`](https://dndkit.com/react/hooks/use-sortable), [sensors guide](https://dndkit.com/react/guides/sensors).
